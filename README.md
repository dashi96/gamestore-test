# Магазин цифровых товаров — тестовое задание, второй этап

Витрина, которая живёт в реальном времени: цены и остатки меняются у всех
открытых вкладок сразу, последнюю единицу получает ровно один покупатель,
а при оформлении товар бронируется на семь минут с отсчётом на экране.

Всё построено поверх первого этапа. Однократная выдача ключа, идемпотентность
вебхуков и восстановление после отказов поставщиков остались на месте, и девять
сценариев проверки гонок из первого этапа проходят без правок логики.

Поднимается одной командой:

```bash
docker compose up
```

- витрина — http://localhost:8080
- админка — http://localhost:8080/admin.html (токен `admin-token`)
- API — http://localhost:3000

Проверка:

```bash
docker compose run --rm races   # 16 сценариев гонок, ничего ставить не надо
npm test                        # логика отбрасывания устаревших ответов
```

## Как посмотреть своими глазами

### Живое обновление витрины

Откройте магазин в двух вкладках, а в третьей — админку. В панели «Живая
витрина» найдите товар по части названия, поменяйте цену или долейте остаток.
Обе вкладки магазина обновятся сами.

То же самое запросом, если удобнее без интерфейса:

```bash
# найти предложение
curl -s 'http://localhost:8080/api/catalog?q=CS2&limit=1'

# поменять цену (offer_id из ответа выше)
curl -s -X POST http://localhost:8080/admin/offers/1997/price \
  -H 'content-type: application/json' -H 'authorization: Bearer admin-token' \
  -d '{"price_rub": 1999}'
```

Зелёная точка «вживую» в шапке показывает состояние потока. Если связь
оборвётся, она станет жёлтой, а рядом появится надпись про потерю связи.

### Гонка за последней единицей

Откройте карточку товара, у которого у продавца осталась одна единица, в двух
вкладках и нажмите «Купить» одновременно. Один покупатель получит страницу
заказа с бронью, второй — сообщение, что товар раскупили, и предложение
другого продавца.

Без ручного тайминга то же самое делает сценарий: двенадцать заказов уходят
параллельно на одну единицу.

```bash
docker compose run --rm races node scripts/races/run-all.mjs 10
```

### Бронь с таймером

Купите любой товар и посмотрите на страницу заказа: идёт отсчёт от семи минут.
Ждать его конца необязательно, срок можно приблизить:

```bash
curl -s -X POST http://localhost:8080/admin/orders/ord_xxxx/expire \
  -H 'authorization: Bearer admin-token' -H 'content-type: application/json' -d '{}'
```

Эта ручка двигает только дедлайн. Снимает бронь по-прежнему развёртка в воркере,
так что проверяется настоящий путь, а не его обход. Через четверть секунды заказ
получит статус «бронь снята», а товар вернётся в продажу во всех открытых
вкладках.

### Цена изменилась, пока товар лежал в корзине

Положите товар в корзину, поднимите цену из админки и вернитесь в корзину.
Строка подсветится, рядом с новой ценой будет зачёркнута прежняя, а на кнопке
появится новая сумма. Заплатить по старой цене нельзя ни при каком стечении
обстоятельств: сумму заказа сервер берёт из предложения в момент захвата
единицы.

### Склад — строки, а не счётчик

В первом этапе остатка в базе не было вовсе: он жил в памяти заглушки
поставщика. «Последняя единица», «один товар не под два заказа» и «кнопка
гаснет у всех» — это утверждения про склад, поэтому склад стал строками.

Продавцов четыре, поставщика по-прежнему два: у товара всегда есть минимум два
предложения, иначе проигравшему гонку нечего было бы предложить. Каждая единица
склада ссылается на слот кода у поставщика, и `/issue` отдаёт по нему один и тот
же код.

Каталог генерируется миграцией: 772 товара, 2316 предложений, 7423 единицы. Сто
предложений пустые намеренно, у 479 ровно одна единица — есть на чём показывать
и погасшую кнопку, и гонку.

### Захват единицы — единственное неочевидное место

```sql
with picked as (
  update stock_units set held_by_order = $2
   where id = (
     select u.id from stock_units u join offers o on o.id = u.offer_id
      where o.id = $1 and u.sold_order_id is null and u.held_by_order is null
      order by o.price_rub, o.id, u.id
      for update of u skip locked
      limit 1
   )
  returning id as unit_id, offer_id
),
held as (
  insert into reservations (unit_id, order_id, price_rub, expires_at, hard_expires_at)
  select p.unit_id, $2, o.price_rub, now() + ..., now() + ...
    from picked p join offers o on o.id = p.offer_id
  returning *
)
select held.*, picked.offer_id from held, picked
```

**Условие доступности целиком относится к строке `stock_units`, и это важно.**

Первая версия выводила доступность из таблицы броней: «нет активной брони на эту
единицу». Рассуждение было такое: конкурент обязан сначала взять ту же строку под
`for update`, значит проверка устареть не может. На нагрузочном прогоне сработала
страховка, то есть двум транзакциям одну единицу взять всё-таки удалось.

Причина в том, что `SELECT ... FOR UPDATE` перепроверяет условие выборки только
по строкам своей таблицы. Первая транзакция берёт блокировку единицы, вставляет
бронь и фиксируется. Вторая успела снять снимок до фиксации первой, брони не
видит, а к моменту блокировки строка уже свободна. Повторной проверки нет:
изменилось условие по чужой таблице, а сама строка склада не менялась.

С признаком занятости на самой строке повторная проверка работает: конкурент
видит занятую единицу, и `skip locked` уводит его к следующей свободной. Таблица
броней осталась историей и подробностями, а источником ответа «свободна ли
единица» быть перестала. Уникальные индексы по броням теперь настоящая
страховка и в норме не срабатывают никогда.

Ноль строк в ответе означает «единиц не осталось». API отвечает `409 sold_out`
и списком других предложений того же товара, отсортированных по цене.

Когда продавец не выбран (заказ по товару, путь первого этапа), тот же запрос
идёт по условию на `sku`: единица берётся из любого предложения, начиная с
самого дешёвого. Выбирать предложение заранее нельзя — десять параллельных
заказов упёрлись бы в одно и то же, пока у соседнего продавца товар свободен.

### Бронь, оплата и что между ними ломается

```
created ──► awaiting_payment ──► paid ──► delivering ──► delivered
   │               │
   │               └── зависший платёж: держится до потолка в 20 минут
   ├── payment_failed        (бронь снята, товар вернулся в продажу)
   └── reservation_expired   (бронь истекла до нажатия «оплатить»)
```

Самая неприятная дыра здесь такая: бронь истекает, пока платёж в полёте.
Покупатель нажал «оплатить» за секунду до конца отсчёта, вебхук пришёл через
две секунды после, а развёртка в этот момент видит заказ ещё неоплаченным и
снимает бронь. Дальше приходят деньги, а товара нет.

Закрыто двумя уровнями. Нажатие «оплатить» переводит заказ в `awaiting_payment`,
и развёртка такие брони не трогает до отдельного потолка. Если первый уровень
всё-таки не сработал, при оплате заказа без активной брони сервер захватывает
любую свободную единицу того же продавца по зафиксированной цене. Свободных нет
— заказ уходит в восстановимый статус, который уже обслуживают воркер и админка.

Этот же второй уровень закрывает последовательность «отказ, потом оплата»:
правило первого этапа «`paid` перебивает `failed`» осталось в силе, но теперь
бронь к моменту оплаты может быть уже снята.

Порядок блокировок везде одинаковый: сначала строка заказа, потом строка
единицы склада. Все переходы брони идут через `core/reservations.ts`, другого
места, где эти две блокировки встречаются, в коде нет.

Освобождает бронь только развёртка. Доступность не смотрит на срок, поэтому
истёкшая, но ещё не снятая бронь держит единицу занятой лишние доли секунды.
Это дешевле, чем разбирать конфликт двух правд о том, свободна единица или нет.

### Живая витрина

Событие несёт полное состояние предложения, а не приращение. Отсюда следует всё
остальное: повтор безвреден, порядок прихода не важен, снимок и поток можно
применять в любой последовательности, а клиент держит максимум номера на каждое
предложение отдельно.

Вставка события идёт после обновления строк, в той же транзакции. Тогда для
одного предложения порядок номеров совпадает с порядком фиксации, потому что их
сериализует блокировка строки. `bigserial` выдаёт номер при вставке, а не при
фиксации, так что для разных предложений порядок может разойтись, и это
безопасно ровно потому, что применяется он по каждому отдельно.

В канал `NOTIFY` уходит только номер: у него восемь килобайт на сообщение, а
состояние читается из `events`. Для живой раздачи курсор не нужен вовсе, он
нужен только там, где события шли мимо: при подключении клиента и после обрыва
слушателя.

Слушатель `LISTEN` живёт на отдельном соединении вне пула, переподключается сам
и выводит своё состояние в `/health`. Без этого признака оборвавшийся слушатель
выглядит как исправный сервис с замершими у всех ценами, а в логах при этом
пусто.

### Почему вебсокет, а не SSE

SSE выглядел уместнее: трафик односторонний, переподключение и докрутка встроены
в протокол, зависимостей ноль, поток читается обычным `curl -N`. Ломает его лимит
браузера — шесть HTTP/1.1-соединений на origin, общих на все вкладки.

При десяти открытых вкладках шесть работают, а четыре повисают в очереди
сокет-пула. Событие `error` при этом не приходит, потому что рвать нечего:
соединение не устанавливалось, и автоматическое переподключение не срабатывает.
Статика раздаётся с того же origin, поэтому седьмая вкладка может не
отрисоваться вообще. В логах сервера чисто: запросы до него не доходят.

Проверено в браузере: десять вебсокетов с одного origin открываются, все
получают событие, и шесть обычных запросов рядом с ними проходят за 60 мс.

### Цена

В корзине нет действующей цены, она подтягивается из предложений, поэтому
устареть ей негде. Рядом лежит только та, которую покупатель видел, когда клал
товар: без неё после перезагрузки страницы подорожание было бы незаметно.

При оформлении клиент присылает цену с экрана. Если она ниже текущей, заказ
проходит молча: отказывать покупателю из-за скидки незачем. Если выше, сервер
отвечает отказом и новой ценой. В момент брони цена копируется в бронь и на
весь её срок не меняется, в этом её смысл.

## Наследство первого этапа

Однократная выдача держится четырьмя независимыми механизмами, и каждый закрывает
свою гонку.

**Двойной клик «Купить».** `UNIQUE` на ключе идемпотентности и вставка через
`ON CONFLICT DO NOTHING`: второй запрос не создаёт заказ, а получает первый.

**Повтор и шторм вебхуков.** `payment_events.event_id` — первичный ключ. Ноль
вставленных строк означает ретрай, и обработчик выходит, ничего не трогая.

**Сам факт выдачи.** `deliveries.order_id` — первичный ключ, двух кодов на один
заказ не существует физически. Рядом `UNIQUE` на самом коде: требование «один
ключ не уходит в два заказа» держится схемой, а не добросовестностью поставщика.

**Таймаут поставщика не равен отказу.** `request_id` детерминирован и не меняется
между попытками, поэтому повтор после таймаута возвращает тот же код.

> К резервному поставщику переключаемся только при однозначном `out_of_stock`.
> Таймаут, обрыв и `5xx` — исход неизвестен, код мог быть уже выдан, поэтому
> повторяем к тому же поставщику с тем же `request_id`.

Промокод расходуется одним атомарным апдейтом с условием `used_count < max_uses`,
без чтения-проверки-записи. Скидку считает только сервер: с клиента приходит одна
строка, код.

Несколько воркеров разбирают очередь через `FOR UPDATE SKIP LOCKED`, так что
гонку можно устроить между процессами:

```bash
docker compose up -d --scale worker=3
docker compose run --rm races
```

| 08 | 10 заказов при 50% ошибок и 30% таймаутов | все выданы, коды уникальные |
| 09 | отказ оплаты, затем `paid` | промокод возвращается и забирается обратно |
| 10 | заказов больше, чем товара; двенадцать на последнюю единицу | ровно один победитель, остальным другой продавец |
| 11 | бронь истекает | товар возвращается всем, подписчики видят это без перезагрузки |
| 12 | обход приложения напрямую в базу | вторая бронь на единицу и вторая единица на заказ невозможны |
| 13 | цена выросла, пока товар в корзине | новая цена видна до оплаты, по старой оформить нельзя |
| 15 | оплата после снятия брони, платёж в полёте, зависший платёж | перезахват, бронь доживает, потолок отпускает |
| 16 | отказ оплаты, потом «оплачено» | заказ всё равно выдан, поздний отказ его не отменяет |
| 17 | обрыв соединения слушателя | `/health` отдаёт 503, слушатель поднимается сам, события не теряются |

Сценария `14` в этом списке нет намеренно: «устаревшие ответы поиска» — чистая
логика без сети, и проверяет её `npm test`, пять случаев вместо одного.

Полный прогон занимает около двух минут. Сценарии `06` и `08` намеренно ждут
исчерпания попыток и самостоятельного восстановления.

## Стек и структура

Node 22 и TypeScript без шага сборки, Fastify, Postgres 16, Vanilla JS на фронте.
Из нового во втором этапе только `@fastify/websocket` и `ws`.

```
server/src/core/     склад, брони, события, поток, оформление, платежи, выдача
server/src/routes/   HTTP-слой и вебсокет, тонкие
server/src/lib/      слушатель LISTEN, база, настройки
provider-stub/       две заглушки поставщика
web/                 витрина, карточка товара, корзина, заказ, админка
scripts/races/       16 сценариев гонок
scripts/tests/       node --test, логика без сети
migrations/          схема и генератор каталога
```

Правки подхватываются без пересборки образа: код примонтирован, процессы под
`tsx watch`, статика отдаётся с `Cache-Control: no-store`.

## Настройки

Стек поднимается без `.env`, значения по умолчанию лежат в `docker-compose.yml`.
Кроме переменных первого этапа появились три:

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `RESERVATION_TTL_SEC` | `420` | срок брони, он же отсчёт на экране |
| `RESERVATION_HARD_TTL_SEC` | `1200` | потолок для заказа, ушедшего в оплату |
| `SWEEP_INTERVAL_MS` | `250` | как часто воркер снимает просроченные брони |

При тестировании удобно поставить срок брони в 30 секунд: `RESERVATION_TTL_SEC=30
docker compose up`.

## Замеры

Поиск по каталогу, полное время ответа API:

| Запрос | Найдено товаров | Время |
| --- | --- | --- |
| `ключ` | 123 | 32 мс |
| `steam` | 22 | 9 мс |
| `подписка` | 160 | 11 мс |

Отдельно про `pg_trgm`. Индекс стоит, но планировщик его не берёт: на 772
названиях последовательный просмотр дешевле, и с принудительно отключёнными
индексными планами время то же, 0,6 против 0,7 мс. То есть миллисекунды выше
уходят не на поиск по тексту, а на подбор лучшего предложения по каждому товару.
Индекс начнёт окупаться на десятках тысяч названий.

Мигание списка при поиске померено через `MutationObserver`. Когда выдача не
меняется, изменений в DOM ноль: узлы переиспользуются и переставляются, только
если действительно оказались не на своём месте. На восемь букв нового запроса
приходится одна смена набора карточек.

## Что намеренно не делалось

По ТЗ: реального эквайринга, проверки подписи вебхука, авторизации покупателя,
отзывов, футера, мобильной и тёмной версий, пересчёта валют.

Количества в корзине нет. Предложение — это лот конкретного продавца, заказ
бронирует одну единицу и получает один код. Количество означало бы несколько
броней на заказ и несколько кодов в выдаче, чего ТЗ не просит.

Корзина без авторизации: `cart_id` в cookie, без истории и переноса между
устройствами. Брошенные корзины воркер убирает через неделю.

Идемпотентность заглушки-поставщика живёт в памяти процесса и теряется при его
перезапуске. Для заглушки это осознанное упрощение.

Вкладки на витрине в первом этапе были декоративными и стали рабочими
фильтрами, а их набор приведён к типам, которые есть в каталоге. Пиксельная
точность по ТЗ не требуется.
