# Магазин цифровых товаров — тестовое задание

Витрина по макету + бэкенд, у которого однократная выдача ключа держится под
параллельными запросами, повторными вебхуками и отказами поставщиков.

Всё поднимается одной командой:

```bash
docker compose up
```

- витрина — http://localhost:8080
- админка — http://localhost:8080/admin.html (токен `admin-token`)
- API — http://localhost:3000

Проверка гонок — тоже одной командой, ничего ставить локально не нужно:

```bash
docker compose run --rm races
```

---

## Ответы по пунктам «что нужно от вас»

**1. Живая версия / запуск.** `docker compose up`, дальше http://localhost:8080.
Поднимаются шесть сервисов: Postgres, миграции, API, воркер выдачи, две
заглушки-поставщика и nginx со статикой. Ничего кроме Docker не требуется.

**2. Исходники.** Этот репозиторий.

**3. Как воспроизвести проверку гонок.** `docker compose run --rm races` —
восемь сценариев, включая все пять из критериев приёмки. Подробности ниже,
в разделе «Проверка гонок».

**4. Как обеспечена однократная выдача.** Четырьмя независимыми механизмами, и
каждый закрывает свою гонку: `UNIQUE` на ключе идемпотентности заказа,
`INSERT ... ON CONFLICT DO NOTHING` по `event_id` вебхука, `deliveries.order_id`
как первичный ключ (двух ключей на заказ не существует физически) и
детерминированный `request_id` к поставщику, из-за которого повтор после
таймаута возвращает тот же самый код, а не новый. Развёрнуто — в разделе
«Однократная выдача».

**5. Сколько времени ушло.** Около шести часов.

## Что сделано по этапам

| Этап | Статус | Где смотреть |
| --- | --- | --- |
| 1. Витрина + базовый флоу выдачи | готово | `web/`, `server/src/routes/shop.ts` |
| 2. Однократная выдача под гонками | готово | `server/src/core/`, `scripts/races/` |
| 3. Сбои и восстановление | готово | `core/delivery.ts`, `provider-stub/`, `web/admin.html` |
| 4. Промокод с лимитом | готово | `core/promo.ts`, `scripts/races/07-promo-limit.mjs` |

Интерактив по макету — все пять точек: карусель баннера (автопрокрутка, стрелки,
активные точки), выпадающее меню «Каталог» (повторный клик и клик вне закрывают),
переключатель валют `$ / ₸ / ₽` (только активное состояние, без пересчёта — как
в ТЗ), плавное выделение иконок сервисов при наведении, подъём и тень карточки
товара. Иконки сервисов, обложки и аватар вынуты из `.fig` макета и лежат
в `web/assets/` — это не подобранные из интернета аналоги. Сам макет в
репозиторий не входит, доставать из него ничего не нужно: всё, что использует
вёрстка, уже извлечено и закоммичено.

## Как устроено

```
браузер ──► nginx (:8080) ──► api (:3000) ──► Postgres
                                  │
                                  ├─ пишет задачу в delivery_jobs
                                  ▼
                             worker (×N) ──► provider-a (:4001)
                                          └─► provider-b (:4002)
```

Вебхук ничего не выдаёт сам: он только фиксирует факт оплаты и ставит задачу в
очередь, после чего сразу отвечает `200`. Выдачей занимается воркер. Это нужно
не ради красоты — платёжка требует быстрого ответа и ретраит по таймауту, а
поставщик может отвечать секундами или не ответить вовсе.

### Статусы заказа

`created → paid → delivering → delivered`, ветки сбоев:

- `created → payment_failed` (промокод возвращается в лимит). Не тупик:
  вебхуки приходят не по порядку, и пришедший позже `paid` поднимает заказ
  обратно — деньги важнее ранее записанного отказа;
- `paid → delivering → out_of_stock` — оплачено, ключей нет. Восстановимо:
  задача остаётся в очереди и после пополнения остатка сама доводит заказ до
  выдачи;
- `paid → delivering → delivery_failed` — выдать не удалось. Тоже восстановимо:
  повторы продолжаются с увеличенным интервалом, плюс в админке есть кнопка
  ручной перевыдачи.

Пул ключей из материалов ТЗ роздан заглушкам-поставщикам (30 ключей у A,
20 у B) — так «остаток закончился» воспроизводится честно, отказом поставщика,
а не переменной внутри приложения.

## Однократная выдача

Четыре механизма, каждый — на своей гонке.

**Двойной клик «Купить».** Клиент генерирует `Idempotency-Key` один раз на
кнопку и не меняет его между повторными отправками. В таблице `orders` на этом
поле стоит `UNIQUE`, вставка идёт через `ON CONFLICT DO NOTHING`: второй запрос
не создаёт заказ, а получает первый. Блокировка кнопки в интерфейсе — только
удобство, защита на сервере.

**Повтор и шторм вебхуков.** `payment_events.event_id` — первичный ключ. Приём
события это `INSERT ... ON CONFLICT (event_id) DO NOTHING RETURNING *`: если
вернулось ноль строк, значит это ретрай, и обработчик выходит, ничего не трогая.
Пятьдесят параллельных вебхуков одного события: один вставил, остальные сорок
девять подождали на блокировке ключа и ушли ни с чем. Обработка идёт в той же
короткой транзакции, под `SELECT ... FOR UPDATE` по строке заказа.

**Сам факт выдачи.** `deliveries.order_id` — первичный ключ. Двух кодов на один
заказ не существует физически, чем бы ни закончилась гонка воркеров. Запись идёт
через `ON CONFLICT (order_id) DO NOTHING`, и если её успел сделать другой
воркер, наш результат просто отбрасывается. Рядом — `UNIQUE` на самом коде:
требование «один ключ не может уйти в два заказа» держится схемой, а не
добросовестностью поставщика. Если он когда-нибудь вернёт уже выданный код,
вставка упадёт, а заказ уйдёт в восстановимое состояние вместо второй выдачи.

**Таймаут поставщика — не отказ.** `request_id` детерминирован:
`req_<order_id>_<provider>`. Он не меняется между попытками, поэтому повтор
после таймаута обязан вернуть тот же код (это записано в контракте поставщика, и
заглушка так и делает: сначала расходует ключ и закрепляет его за `request_id`,
и только потом «зависает»). Отсюда же следует политика фолбэка:

> К резервному поставщику переключаемся **только** при однозначном
> `out_of_stock`. Таймаут, обрыв и `5xx` — исход неизвестен, код мог быть уже
> выдан, поэтому повторяем к тому же поставщику с тем же `request_id`.

Переключение на B по таймауту выглядело бы «отказоустойчивее», но именно оно и
приводит к двойной выдаче: A мог успеть выдать ключ. Поэтому `delivery_failed`
наступает, когда попытки к текущему поставщику исчерпаны, — это чуть строже
формулировки «оба поставщика не смогли» из ТЗ, и разница здесь намеренная.

**Промокод под гонкой** — один атомарный апдейт, без чтения-проверки-записи:

```sql
update promocodes set used_count = used_count + 1
 where code = $1 and used_count < max_uses returning *;
```

Ноль строк — лимит исчерпан. Строку блокирует сам Postgres, поэтому тридцать
параллельных запросов с `LIMIT3` дают ровно три успеха. Скидку считает только
сервер: с клиента приходит одна строка — код, ни цена, ни размер скидки не
принимаются вообще.

**Несколько воркеров.** Задачи забираются через `FOR UPDATE SKIP LOCKED`, так
что гонку можно устроить по-настоящему, между процессами:

```bash
docker compose up -d --scale worker=3
docker compose run --rm races
```

Набор проходит одинаково и на одном воркере, и на трёх.

## Проверка гонок

```bash
docker compose run --rm races                                   # все сценарии
docker compose run --rm races node scripts/races/run-all.mjs 06 # только выбранные
npm run races                                                   # с хоста, если стек уже поднят
```

| # | Сценарий | Что проверяется |
| --- | --- | --- |
| 01 | 20 параллельных «Купить» с одним ключом идемпотентности | создан ровно один заказ |
| 02 | 50 параллельных вебхуков по одному заказу — с одним `event_id` и с пятьюдесятью разными | один факт выдачи, израсходован один ключ |
| 03 | повтор того же `event_id` спустя время | ничего не меняется, ответ 200, код прежний |
| 04 | вебхук пришёл раньше создания заказа | событие припарковано и применено позже, без потери и дубля |
| 05 | пустой пул у обоих поставщиков | `out_of_stock` без падения, видно в админке, после пополнения — ровно один ключ; повторные нажатия идемпотентны |
| 06 | поставщик выдал код и завис + полный отказ обоих | тот же код после повтора, к резервному не ушли, `delivery_failed` восстанавливается сам |
| 07 | `ONCEONLY` ×25 и `LIMIT3` ×30 параллельно | применено ровно `max_uses` раз, скидку посчитал сервер |
| 08 | 10 заказов при 50% ошибок и 30% таймаутов | все выданы, коды уникальные, очередь пуста |
| 09 | отказ оплаты, затем `paid` по тому же заказу | промокод возвращается в лимит и забирается обратно, `paid` перебивает `failed` в любом порядке |

Критерии приёмки из ТЗ закрываются сценариями 02, 03, 04, 05 и 07
соответственно.

Прогон занимает две-три минуты: сценарии 06 и 08 намеренно ждут исчерпания
попыток и самостоятельного восстановления, а не форсируют его руками.

### Руками, через интерфейс

1. На витрине нажать «Купить» — откроется страница заказа.
2. «Отправить вебхук 50× параллельно» — в логе будет `accepted: 1,
   duplicate: 49`, а заказ получит один код.
3. В админке кнопками «Опустошить», «Ломать», «Вешать» можно довести заказ до
   `out_of_stock` или `delivery_failed`, а потом вернуть в строй «+5 ключей» и
   «Выдать повторно». Повторные нажатия ничего не задваивают.

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/products` | каталог |
| `POST` | `/api/orders` | создать заказ; заголовок `Idempotency-Key`, тело `{sku, promo_code?}`. Необязательный `order_id` позволяет задать номер заранее — этим воспроизводится вебхук, пришедший раньше заказа |
| `GET` | `/api/orders/:id` | статус заказа и код |
| `POST` | `/api/promo/quote` | предпросмотр скидки (ничего не расходует) |
| `POST` | `/api/orders/:id/pay` | заглушка оплаты: шлёт вебхук(и) по контракту |
| `POST` | `/webhook/payment` | приём вебхука платёжной системы |
| `GET` | `/admin/orders?scope=stuck` | «оплачен, но не выдан» |
| `POST` | `/admin/orders/:id/redeliver` | ручная перевыдача (идемпотентная) |
| `GET` | `/admin/providers` | остатки и статистика поставщиков |
| `POST` | `/admin/providers/:id/config` | доля ошибок и таймаутов |
| `POST` | `/admin/providers/:id/stock` | пополнить или опустошить остаток |
| `POST` | `/admin/reset` | сброс состояния (для прогонов) |

Админские ручки — по `Authorization: Bearer admin-token` (меняется переменной
`ADMIN_TOKEN`).

## Стек и структура

Node 22 + TypeScript (запуск через `tsx`, без шага сборки), Fastify, Postgres 16,
чистый Vanilla JS на фронте — без сборщика и фреймворков.

```
server/           API, воркер выдачи, миграции
  src/core/       заказы, платежи, выдача, промокоды — вся логика здесь
  src/routes/     HTTP-слой, тонкий
provider-stub/    две заглушки поставщика по контракту из ТЗ
web/              витрина, страница заказа, админка
scripts/races/    сценарии проверки гонок
migrations/       схема и сиды
```

Правки в `server/`, `provider-stub/` и `scripts/` подхватываются без пересборки
образа: код примонтирован, процессы под `tsx watch`.

## Настройки

| Переменная | По умолчанию | Смысл |
| --- | --- | --- |
| `ADMIN_TOKEN` | `admin-token` | токен админки |
| `PROVIDER_TIMEOUT_MS` | `2000` | когда считаем, что ответ поставщика не дошёл |
| `MAX_DELIVERY_ATTEMPTS` | `5` | попыток до перехода в `delivery_failed` |
| `A_ERROR_RATE` / `A_TIMEOUT_RATE` | `0.15` / `0.1` | «характер» поставщика A |
| `B_ERROR_RATE` / `B_TIMEOUT_RATE` | `0.15` / `0.1` | то же для B |

## Что намеренно не делалось

По ТЗ: реального эквайринга, проверки подписи вебхука, авторизации покупателя,
отзывов, футера, мобильной и тёмной версий, пересчёта валют. Дизайн страницы
заказа и админки — рабочий вид без оформления. Меню «Каталог» открывается и
закрывается, детальная вёрстка колонок упрощена.

Идемпотентность поставщика-заглушки живёт в памяти процесса: при его перезапуске
карта `request_id → код` теряется. Для заглушки это осознанное упрощение — у
настоящего поставщика она на его стороне.
